# 沟通的本质

让**正确的信息**、在**正确的时间**、以**正确的形式**、到达**正确的人**

- **降低协作摩擦**：PR 评审快、设计顺、少扯皮
- **减少返工**：需求澄清阶段签清 AC
- **放大技术影响力**：好方案靠讲清才被采纳
- **冲突可控**：数据驱动而非立场对抗

> 沟通是资深工程师与初级工程师的分水岭

<!--
技术深度决定解决多难的问题，沟通广度决定调动多少人。
-->

# 沟通是资深分水岭

| 能力层级 | 关注点 | 沟通特征 |
|---|---|---|
| 初级 | 把功能做出来 | 听清需求，问对问题 |
| 中级 | 把模块设计好 | 写清设计文档 |
| 高级 | 推动系统/团队 | 跨团队协调 |
| Staff+ | 做大杠杆的事 | 愿景沟通 |

> 技术深度 × 沟通广度 = 影响力天花板

<!--
只会写代码的工程师有天花板，能协调的没有。

# 代码评审：对事不对人

| ❌ 针对人 | ✅ 针对代码 |
|---|---|
| 「你这里写错了」 | 「X 情况下返回 null，建议判空」 |
| 「为什么这么乱」 | 「函数 3 个职责，可否拆分」 |

**建设性反馈四要素**

1. 观察（事实）→ 2. 影响 → 3. 建议 → 4. 提问

> 用「我们」「建议」而非「你」「错了」

<!--
评审评论针对代码与决策，不针对人。
-->

---

# 评审意见分级（关键）

未分级的评审是灾难——作者不知哪些必须改

| 级别 | 含义 | 处理 |
|---|---|---|
| **Blocking** | 必须改（bug/安全） | 合并前必须解决 |
| **Suggestion** | 建议改（更好实践） | 作者决定 |
| **Nit** | 吹毛求疵（格式） | 可忽略 |
| **Praise** | 点赞好实践 | 鼓励正向反馈 |

> 每条评论应**显式标明级别**

<!--
分级让作者知道优先级，避免过度修改或忽略关键。
-->

# ADR 架构决策记录

轻量级设计决策记录，一个文件一个决策

```markdown
# ADR-042: 使用 PostgreSQL 而非 MongoDB

## 状态  已接受（2026-07-15）
## 背景  订单需强一致性事务
## 决策  采用 PostgreSQL 14
## 后果  正:强一致 / 负:需 ORM
```

**四要素**：状态 / 背景 / 决策 / 后果

- 放 `docs/adr/`，纳入版本控制
- 状态随决策演进（提议→接受→废弃）

> 三个月后知道「为什么这么定」

<!--
ADR 让决策可追溯、可质疑、可演进。
-->

# 需求澄清与 AC

「做完了才发现不是想要的」是**最贵的返工**

**AC（验收标准）**——明确「做完」的定义

```
用户故事：运营导出订单报表做月度结算
AC：
1. 按日期范围筛选订单
2. 导出 CSV，含订单号/金额/状态
3. 单次上限 10 万行，超则分批
4. 异步执行，完成邮件通知
```

> AC 签订后，开发/产品/测试对「完成」有共识

<!--
澄清发生在编码前，成本最低。
-->

# 向上汇报三段式

给决策者**选项 + 推荐**，而非抛问题

```
1. 背景 + 问题（1-2 句）
2. 选项 A/B/C（ROI、成本、风险）
3. 我的推荐 + 理由
```

**进度汇报**：红黄绿状态

- Green 正常 / Yellow 有风险 / Red 需帮助
- Yellow/Red 必须附**缓解措施**

> 坏消息早说，藏到爆雷是最大失职

<!--
管理者要决策支持，不是把问题甩上去。
-->

# 冲突管理：数据驱动

技术冲突忌「我觉得 vs 你觉得」立场拉锯

| ❌ 立场对抗 | ✅ 数据驱动 |
|---|---|
| 「我的方案更好」 | 「基准测试 P99 低 40%」 |
| 「大家都这么觉得」 | 「3 个负责人反馈 X，见链接」 |

**用 RFC 书面化讨论**

- 动机 / 提案 / 备选 / 权衡 / 开放问题
- 聚焦方案而非人，分歧可追溯

> 「不同意但承诺执行」——决策后全力执行

<!--
RFC 让讨论聚焦于方案而非人。
-->

# 异步沟通：BLUF 结论先行

**BLUF（Bottom Line Up Front）**——结论放最前

```
【结论】需要你批准 B 方案人力（3 人周）
【背景】订单库 QPS 8000 逼近上限
【选项】A/B/C 对比
【推荐】B，ROI 最高
```

**结构化表达**

- 金字塔原理：结论 → 分论点 → 论据
- 列表优于段落，加粗关键信息

> 消息要让对方**一条看完就能回**

<!--
异步沟通的核心是结论先行、结构化。
-->

# 跨团队协作：契约先行

最大成本是**假设不一致**——先定义接口契约

- **OpenAPI** 描述 HTTP API，生成 mock + 文档
- **Protobuf/Avro** 描述事件/消息
- 契约变更走**版本化** + deprecation 期

**边界对齐**

- 明确所有权边界（哪个团队负责什么）
- 设**对接人**，避免「找谁都不知道」

> 双方基于契约并行开发，变更走 RFC

<!--
接口契约是跨团队协作的基石。
-->

# 三本核心书落地

| 书 | 核心思想 | 落地 |
|---|---|---|
| Clean Code | 命名即沟通 | `getExpiredUsers()` 优于 `getData()` |
| Pragmatic | 隐喻与责任 | 破窗效应：坏沟通传染 |
| Staff Engineer | 影响超出代码 | 写下来放大影响 |

> 好沟通让好技术被看见，但无法替代技术本身
